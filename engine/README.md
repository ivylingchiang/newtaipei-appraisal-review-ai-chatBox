# engine — 估價案件審查規則引擎

讀取 [`datasets/`](../datasets/)，對估價書表執行跨表一致性檢查與查表核算，
並在資料不足時推導可計算的部分、明確標示缺口。

```bash
python3 engine/cli.py                 # 全部區域
python3 engine/cli.py shulin          # 指定區域
python3 engine/cli.py jinshan --no-derive
python3 engine/cli.py shulin --json   # 機器可讀輸出
python3 engine/test_engine.py         # 正向 + 反向測試
```

離開碼：有 `error` 時為 1，否則 0（可直接接 CI）。

---

## 1. 兩種模式

| 模式 | 輸入 | 輸出 |
|---|---|---|
| **審查** | 已填的表3/表4/表5 | 逐條 finding（R1/R2/R4/R6/R7/R12/R14/PRICE/CR1/CR2） |
| **輔助填表** | 表3 觀測值 + 基準明細表 | 推導表5 的優劣等級與修正百分比，並列出無法計算的項目與原因 |

兩種模式同時執行：審查既有內容，同時算出應有的值。

## 2. 檢查項目

對應作業手冊「審查重點」，完整矩陣見 [`datasets/common/review_rules.json`](../datasets/common/review_rules.json) 之 R1~R14 跨表參照矩陣。

| 規則 | 內容 | 手冊審查重點 |
|---|---|---|
| **R1** | 表3 所載優劣等級 ↔ 表5 優劣等級一致 | vi |
| **R2** | 表5 修正百分比 = 依區域因素基準明細表查得之值 | vi |
| **R4** | 表5 總修正數 = 表4 區域因素調整百分率 | vii |
| **R6** | 表4 個別因素差異率 = 依個別因素基準明細表查得之值 | vii |
| **R7** | 權重邏輯（絕對值加總愈大→權重愈小；合計 100%）、絕對值加總重算 | vii |
| **R12** | 各用地別應評價細項是否具備可判定資料 | iii |
| **R14** | 表5 各項小計加總 = 總修正數 | vi |
| **PRICE** | 價格鏈重算：調整至基準日單價、試算價格 | vii |
| **CR1** | 捷運開發區以變更前分區認定 | — |
| **CR2** | 8m 以下道路旁住宅區基準容積率 200% | — |

### 嚴重度

| 等級 | 意義 | 處理 |
|---|---|---|
| `error` | 與基準表／跨表數值明確不符 | 應退補更正 |
| `warning` | 資料不齊或規則不相容 | 需人工確認 |
| `blocked` | 欄位空白，無法核算 | 非錯誤，屬缺件 |
| `info` | 已套用案件規則之說明 | 供審查者知悉 |

**設計原則**：資料不足回報 `blocked` 而非 `error`。
把「沒填」誤判為「填錯」會讓審查者失去對系統的信任。

## 3. 判級與查表

```
表3 事實 ──grade()──> 優劣等級 rank ──adjust()──> 修正百分比
```

查表方向**表5 與表4／表6 相同**，共用同一函式：

| 用途 | 函式 | 公式 | 正負意義 | 方向依據 |
|---|---|---|---|---|
| 表5 區域因素<br>表4／表6 個別因素 | `adjust()` | (比較標的級距 − 比準地級距) × 級距差<br>≡ `matrix[比準地−1][比較標的−1]` | 比較標的較劣 → **正** | 金山官方已填範本 表4 五筆非零細項 |

> **一段曾走錯的路**：曾把表5 拆成 `adjust_regional()`、改採相反方向，理由是「表5-1 同列
> 並置等級序號與修正百分比，兩者正負須一致」。經承辦單位澄清該判斷為誤判，已回復單一方向。
> 需注意金山官方範本的表5 **無法驗證方向** —— 其比較標的與比準地逐項同級，修正百分比全為
> `0.00`，正反兩個方向都對得上；唯一可反算的證據是表4 的五筆非零細項。

`grading.grade()` 依序嘗試四種比對，確保各種填寫慣例都能對上：

1. **級距原文完全相符** — 表3 常直接抄錄基準表文字（「平均坡度未滿5度」）
2. **類別完全相符** — 「不可路邊停車」
3. **類別最長包含相符** — 「第一種住宅區」→ 級距「住宅區」
4. **數值落入級距** — 距離／面積／百分比，另支援 `in_segment`、`is_none`

> 第 2 步必須先於第 3 步。單靠子字串會出錯：「可路邊停車」是「不可路邊停車」的
> 子字串，寬鬆比對會把「不可路邊停車」判成「優」。這是實際踩到並修掉的 bug。

**「無此設施」的判級**（`threshold._match_none`）：
基準表多以「2000m以上或無」明列；少數（金山商業之環境污染、廢棄物處理設施）
只寫距離級距。後者依語意處理 —— 無設施＝距離無限遠 —— 落在上界開放的那一級。

## 4. 驗證

`python3 engine/test_engine.py`

### 正向：官方已填範例必須零錯誤

金山案（`查估書表範本.pdf`）是主管機關的完整正解，跑出任何 `error` 都代表引擎有 bug。
**目前 0 error。** 開發過程中這項測試抓出兩個真實缺陷：

- 表5 小計列 `因素(8) 百分比小計` 的群組編號 `(8)` 被當成數值
- 類別判級的子字串誤判（見 §3）

### 反向：注入錯誤必須被抓到

不會叫的看門狗沒有價值。測試對正解注入 7 種已知錯誤，每種都必須觸發對應規則：

| 注入的錯誤 | 期望觸發 | 結果 |
|---|---|---|
| 表5 修正率 7.5 → 0.0 | R2 | ✅ |
| 表4 區域因素調整率 0.0 → 3.21 | R4 | ✅ |
| 表4 面前道路寬度差異率 5.0 → 2.5 | R6 | ✅ |
| 表4 深度條件改為 55m，差異率未同步 | R6 | ✅ |
| 表5 小計竄改為 2.5 | R14 | ✅ |
| 單一比較標的權重改為 80% | R7 | ✅ |
| 試算價格改為 999,999 | PRICE | ✅ |

### 推導結果驗證

樹林案的推導值以人工可複核的方式斷言：

- 容積率：P001-00 260%（普通,3）vs P002-00 200%（稍劣,4）→ (4−3)×6.25 = **+6.25%**
- 主要道路：P001-00 28m（優,1）vs P002-00 7m（劣,5）→ (5−1)×3.75 = **+15.00%**
- 期望值由基準表 `step` 獨立推算，不抄引擎輸出；查表方向反了必然失敗
- 表4 方向另以金山官方範本五筆非零細項斷言（面前道路寬度 +5.00% 等），
  並斷言表5 與表4 同向，防止日後又被拆成一正一反
- 資料不足時 `complete=False`，不得標記為完整

## 6. 模組

| 檔案 | 職責 |
|---|---|
| `loader.py` | 載入資料集（基準表、區段、案件、共用規則） |
| `grading.py` | 判級與查表（`grade` / `adjust` / `split_conditions`） |
| `checks.py` | R1~R14、CR1/CR2、價格鏈檢查，回傳 `Finding` |
| `compute.py` | 由表3 推導表5（含缺口原因） |
| `review.py` | 主流程與報表格式 |
| `cli.py` | 命令列介面 |
| `export.py` / `export_xlsx.py` | 第一、二版輸出（分析報表／回填 Excel 範本） |
| `export_v3.py` / `export_v4.py` | 第三、四版（表3 設施欄、表4 個別因素 13~21） |
| `export_final.py` | 交付版：比照金山區範本之填寫方式產生表3／表4／表5 及其 PDF |
| `export_pdf.py` | 依工作表版面把已填 xlsx 排成黑白 PDF（不需 Excel／LibreOffice） |
| `test_engine.py` | 正向＋反向測試 |
